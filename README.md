# Формы откликов — конструктор форм для карьерной платформы студентов

Менеджер сам собирает форму отклика на стажировку или мероприятие, публикует её по уникальной ссылке
и смотрит ответы и конверсию. Студент открывает ссылку (с компьютера или телефона) и отправляет ответы.
Разработчики для новой формы больше не нужны.

## Быстрый старт

Требуется **Node.js 20.9+** (минимальная версия для Next.js 16) и npm. Из корня репозитория:

```bash
npm install
```

```bash
npm start
```

`npm start` собирает production-сборку (`next build`, ~15–30 с) и запускает сервер.
После строки `✓ Ready` сервис доступен на **http://localhost:3000**:

| Что | Адрес |
|---|---|
| Админка (без авторизации) | http://localhost:3000/admin |
| Публичная форма | `http://localhost:3000/f/<publicId>` — ссылку выдаёт админка после публикации |

Другой порт задаётся переменной `PORT`:

```bash
PORT=4000 npm start
```

(Windows PowerShell: `$env:PORT=4000; npm start`.)

Никаких API-ключей, облачных сервисов и отдельной СУБД не нужно: данные хранятся в файле `data/db.json`
внутри проекта, шрифты поставляются npm-пакетом, сборка работает без интернета.

## Как создать и опубликовать форму

1. Откройте `/admin` → **«Создать форму»**.
2. Во вкладке **«Конструктор»** задайте название и описание, добавьте вопросы из панели «Добавить поле»
   (или кнопкой «Добавить базовые поля»). Для каждого вопроса: текст, подсказка, плейсхолдер, обязательность,
   тип; для списков — варианты ответа. Порядок меняется стрелками ↑/↓, вопрос можно дублировать и удалить.
3. **«Сохранить»** (или Ctrl/Cmd+S). Вкладка **«Предпросмотр»** показывает форму глазами студента,
   включая несохранённые правки (в режиме «Телефон» — как на мобильном).
4. **«Опубликовать»** → появится публичная ссылка с кнопками «Копировать» и «Открыть».
5. Студенты заполняют форму по ссылке. Ответы — во вкладке **«Ответы»** (таблица, карточка ответа,
   экспорт CSV), воронка заполнения — во вкладке **«Аналитика»**.
6. **«Снять с публикации»** закрывает приём ответов: ссылка показывает «Форма сейчас не принимает ответы».

## Возможности

- **10 типов полей:** короткий и длинный текст, email, телефон, число (с мин./макс.), выпадающий список,
  один из списка, множественный выбор, дата, флажок-согласие.
- **Серверная валидация** по актуальной схеме формы: обязательность, формат email/телефона/даты, тип и диапазон
  числа, допустимые варианты. Клиент использует тот же модуль (`lib/schema.ts`) для мгновенных подсказок,
  но сервер ему не доверяет.
- **Неопубликованные формы** не отдают содержимое и не принимают ответы (403).
- **Защита от двойной отправки:** кнопка блокируется, а повтор с тем же `submissionId` возвращает уже
  сохранённый ответ, не создавая дубликат.
- **История ответов не ломается при редактировании формы:** каждый ответ хранит снимок вопросов на момент
  отправки — переименованные и удалённые вопросы и варианты отображаются так, как их видел студент.
- **Форма изменилась во время заполнения:** сервер отвечает `409 FORM_CHANGED`, форма перерисовывается,
  уже введённые ответы сохраняются.
- **Две вкладки админки:** устаревшее сохранение отклоняется (`409 VERSION_CONFLICT`), а не перезаписывает чужие правки.
- **Аналитика конверсии** (см. методику ниже) и **экспорт CSV** (UTF-8 с BOM для Excel, защита от формул).
- Адаптивный интерфейс, доступность: подписи, `fieldset/legend`, `aria-invalid`/`aria-describedby`,
  сводка ошибок с фокусом на первом поле, видимые фокус-кольца, крупные зоны нажатия на телефоне.

### Методика аналитики

Цифры считаются только по реальным событиям, ничего не достраивается:

- **Просмотр** — форма отрисовалась у студента (один раз за сеанс вкладки; сеанс хранится в `sessionStorage`,
  поэтому перезагрузка не удваивает просмотры).
- **Начало заполнения** — студент впервые **изменил значение** любого поля (не фокус и не загрузка страницы).
- **Отправка** — успешно сохранённый ответ.
- **Конверсия** = отправившие из начавших. По каждому вопросу — сколько сеансов его заполнили и на скольких
  брошенных сеансах он был последним, к которому студент приступил: так видно, где студенты уходят.
- В предпросмотре события не отправляются. Если данных нет, показывается «—», а не 0%.

## Архитектура

**Next.js 16 (App Router) + TypeScript + Tailwind CSS 4** — проект создан официальным генератором
`create-next-app` со стандартной структурой. Один процесс обслуживает и интерфейс, и JSON API (route handlers).

```
app/
  admin/                    админка: список форм и редактор (/admin/forms/[id]?tab=…)
  f/[publicId]/             публичная форма студента
  api/forms/**              админ-API: CRUD, публикация, ответы, CSV, аналитика
  api/public/forms/**       публичное API: схема формы, отправка ответа, события аналитики
  api/[...slug]/            JSON-404 для неизвестных маршрутов API
components/                 UI: конструктор, вкладки редактора, FormRenderer (общий для предпросмотра и публичной формы)
lib/schema.ts               общая схема: типы полей, нормализация формы, валидация ответов (клиент + сервер)
lib/server/store.ts         файловое хранилище data/db.json
lib/server/forms.ts         бизнес-логика: формы, ответы, CSV, аналитика
lib/server/http.ts          формат ошибок, лимит тела запроса, проверка Origin, rate limit
docs/API.md                 полный API-контракт
test/                       unit- и HTTP-тесты
```

### Модель данных и хранение

`data/db.json` содержит три коллекции:

- `forms` — `id` (для админки), `publicId` (10 случайных символов для ссылки), `title`, `description`,
  `fields[]`, `status` (`draft`/`published`), `version` (растёт при каждом сохранении), даты.
- `responses` — `formId`, `submissionId`, `answers` (по id полей), `formVersion` и `fields` — снимок вопросов
  на момент отправки.
- `sessions` — сеансы аналитики: когда открыли, начали, отправили, какие поля трогали.

Почему JSON-файл, а не SQLite: npm 11 по умолчанию блокирует install-скрипты пакетов, и нативные драйверы
SQLite могут не собраться у проверяющего — это нарушило бы запуск «двумя командами». Надёжность файла обеспечена так:

- изменения выполняются строго по очереди над черновой копией данных; копия пишется **атомарно**
  (временный файл → `fsync` → `rename`) и только после успешной записи становится текущим состоянием —
  при сбое записи в памяти не остаётся «фантомных» данных, а клиент получает ошибку;
- повреждённый файл не теряется: он переименовывается в `db.corrupt-<время>.json`, сервер стартует с пустой базой;
- все route handlers используют один экземпляр хранилища на процесс.

### Защита публичных маршрутов

Лимит тела запроса 200 КБ (проверяется потоково), не более 30 отправок и 600 событий в минуту с одного IP
на форму, до 10 000 ответов и 20 000 сеансов аналитики на форму, проверка `Origin` для изменяющих
запросов админ-API (защита от CSRF), отбрасывание неизвестных полей ответа, запрет id вида `__proto__`,
нейтрализация формул в CSV. Пользовательский текст выводится только как текст.

## Тесты и проверки

```bash
npm test
```

Собирает проект и запускает 58 тестов (vitest; **для тестов нужен Node.js 22.12+** — требование vitest 5,
на сам запуск приложения это не влияет):

- `test/schema.test.ts` — 21 unit-тест схемы и валидации всех типов полей;
- `test/store.test.ts` — 8 тестов хранилища: перезагрузка, очередь записей, сбой записи без фантомных данных,
  повреждённый файл, очистка временных файлов;
- `test/api.test.ts` — 29 контрактных HTTP-тестов против настоящего `next start` на случайном `PORT`:
  CRUD, порядок полей, публикация, 403 для черновиков, 404, отклонение пустых обязательных полей,
  некорректного email и значений неверного типа, идемпотентность, снимки схемы, CSV, аналитика, 409, 413, 429,
  CSRF, перезапуск сервера с сохранением данных.

Дополнительно выполнено вручную (браузерный E2E на свежем `git clone` → `npm install` → `npm start`):
создание формы, добавление и переупорядочивание полей, сохранение, предпросмотр, ссылка на неопубликованную
форму («не принимает ответы»), публикация, заполнение на мобильной ширине 375 px (ошибки обязательных полей
и неверного email, успешная отправка), неизвестная ссылка («Форма не найдена»), ответ и аналитика в админке,
перезапуск на `PORT=4567` с сохранением данных. Проверки типов и линтер: `npx tsc --noEmit`, `npm run lint`.

## Известные ограничения

- Админка без авторизации — по условию задания. Любой, кто знает адрес `/admin`, может управлять формами.
- Хранилище рассчитано на один процесс сервера и умеренные объёмы (весь файл держится в памяти и переписывается
  при каждом изменении); для продакшена следующий шаг — SQLite/PostgreSQL.
- Аналитика best-effort: идентификатор сеанса генерирует браузер, поэтому накрутку можно ограничить
  лимитами, но не исключить. Отправки без сеанса (например, при заблокированных событиях) учитываются
  в «Отправили», но не в воронке.
- `npm start` каждый раз пересобирает проект (так требует контракт «двух команд»); для повторного запуска
  без сборки есть `npm run serve`.
- TypeScript 7 пока не поддерживается typescript-eslint, поэтому по рекомендации команды TypeScript
  используется схема side-by-side: `tsc` — версия 7 (пакет `@typescript/native`), а имя `typescript`
  указывает на совместимый пакет `@typescript/typescript6` для линтера и Next.js.
